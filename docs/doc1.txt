1. Executive Summary

This document describes the complete, production-grade architecture of an algorithmic options buying bot designed exclusively for the Indian derivatives market. The system simultaneously trades weekly and monthly options on NIFTY 50 (NSE) and BANKNIFTY (NSE) using AngelOne SmartAPI as the brokerage gateway.

The bot is designed as a fully automated, intraday-only system that ingests real-time market data, processes it through multiple signal-generation strategies, validates each opportunity against a multi-layered risk framework, executes orders with precision, and monitors live positions for optimal exit conditions — all while streaming real-time alerts and maintaining detailed trade logs.



1.1 Scope & Objectives

Simultaneous Coverage: Trade NIFTY and BANKNIFTY options in parallel with independent signal engines and shared risk budgets.

Intraday Only: All positions are opened and closed within the same trading session (9:15 AM – 3:20 PM IST) to eliminate overnight theta risk.

Options Buyer Mindset: The system buys CE/PE options with controlled premium outlay, maximising the reward-to-risk ratio.

Latency Target: End-to-end signal-to-order latency under 500 milliseconds.

Capital Safety: Hard daily loss limits enforced at broker level and application level.

2.2 Component Interaction Map

The following describes the data and control flow between components:

AngelOne SmartAPI WebSocket streams live ticks for all subscribed tokens (NIFTY, BANKNIFTY spot + options chain).

Feed Manager normalises each tick and routes it to two parallel processing pipelines — one for NIFTY, one for BANKNIFTY.

The Option Chain Parser continuously updates a live snapshot: LTP, OI, IV, bid/ask, volume, PCR for each strike.

The Greeks Engine recomputes Delta, Theta, Gamma, Vega on each relevant tick, caching results.

Each Strategy Module polls the latest enriched snapshot and emits a Signal object when conditions are met.

The Risk Manager evaluates the Signal against daily P&L, open positions, IV Rank, time constraints, and capital limits before approving.

On approval, the Execution Engine fetches a fresh LTP, constructs a LIMIT order, and submits it to AngelOne NFO.

The Position Monitor tracks each open position in real-time against SL, trailing SL, target, and time-based exit rules.

All events are logged to the database and critical events trigger Telegram notifications.

3. Module 1 — Authentication & Session Management

AngelOne SmartAPI requires a multi-step authentication process combining API credentials, a password, and a time-based one-time password (TOTP). Session tokens have a finite validity window and must be renewed proactively.



3.1 Authentication Flow

Step 1 – TOTP Generation: Uses the TOTP secret stored in .env to generate a 6-digit OTP via pyotp library (RFC 6238 compliant, 30-second window).

Step 2 – Session Creation: Calls SmartAPI generateSession() with API_KEY, CLIENT_CODE, PASSWORD, and TOTP. Returns jwtToken, refreshToken, and feedToken.

Step 3 – Token Storage: Stores jwtToken (used for REST calls), refreshToken (for renewal), and feedToken (for WebSocket authentication) in a thread-safe SessionStore.

Step 4 – Token Refresh: JWT tokens expire every 24 hours. APScheduler renews the token at 8:55 AM daily, 20 minutes before market open.

Step 5 – WebSocket Auth: The SmartWebSocket instance is initialised with AUTH_TOKEN and CLIENT_CODE at bot startup.

4.4 Expiry Calendar Logic

The bot must correctly handle weekly and monthly expiries for both instruments:

Thursday (NIFTY Weekly): NIFTY has weekly expiries every Thursday. If Thursday is a holiday, expiry shifts to Wednesday.

Wednesday (BANKNIFTY Weekly): BANKNIFTY has weekly expiries every Wednesday. If Wednesday is a holiday, expiry shifts to Tuesday.

Monthly Expiry: The last Thursday (NIFTY) and last Wednesday (BANKNIFTY) of each month is the monthly expiry.

0DTE Detection: The registry detects when the nearest expiry falls on today's date and flags it as a 0DTE (zero days to expiry) instrument. The risk manager applies stricter rules for 0DTE trading.

NSE Holiday Calendar: A YAML-configured list of NSE trading holidays is maintained. The registry skips holidays when computing expiry dates.

5.2.2 Token Subscription Strategy

At market open, the bot subscribes to Mode 3 for 5 strikes ITM and 5 strikes OTM for both CE and PE for both NIFTY and BANKNIFTY — totalling approximately 40 tokens.

As spot price moves, the subscription list is dynamically updated to keep ATM +/- 5 strikes in Mode 3 and move distant strikes to Mode 1.

WebSocket heartbeat is sent every 30 seconds. If no data is received for 60 seconds, the bot triggers an automatic reconnect.

On reconnect, the bot re-subscribes to all active tokens and marks any missed ticks as a data gap in the log.

5.3.2 IV Rank Computation

IV Rank = (Current IV - 52-week Low IV) / (52-week High IV - 52-week Low IV) × 100

Computed for ATM strikes of both NIFTY and BANKNIFTY every 5 minutes.

Stored in a rolling database table. Used by the risk manager to block buying when IV Rank > 50.

IV Percentile (alternative): Percentage of days in the past year where IV was lower than current IV.

6. Module 4 — Greeks Engine

The Greeks Engine is the analytical core of the options trading system. It computes all Black-Scholes option Greeks using live market data and provides critical filters for strike selection, entry viability assessment, and position risk quantification.



6.1 Black-Scholes Implementation

The engine implements the Black-Scholes-Merton model adapted for index options (continuous dividend yield approximation):

d1 = [ln(S/K) + (r - q + 0.5σ²)T] / [σ√T]

d2 = d1 - σ√T



Call Price = S·e^(-qT)·N(d1) - K·e^(-rT)·N(d2)

Put  Price = K·e^(-rT)·N(-d2) - S·e^(-qT)·N(-d1)



Where: S=Spot, K=Strike, r=Risk-free rate (~6.5% India),

       q=Dividend yield (~1.5% for NIFTY), T=Time to expiry (years),

       σ=Implied Volatility, N()=Standard Normal CDF

6.3 Implied Volatility Extraction

IV is not directly observable — it must be solved iteratively from the observed market price of the option:

Method: Newton-Raphson numerical solver (converges in 5-10 iterations for reasonable market prices).

Seed: The previous tick's IV is used as the initial guess to accelerate convergence.

Bounds: IV is bounded between 0.01 (1%) and 5.0 (500%) to prevent solver divergence.

Fallback: If Newton-Raphson fails to converge, Brent's method (bisection) is used as a fallback.

Cache: IV values are cached with a 1-second TTL to avoid recomputation on every tick.



6.4 Strike Viability Assessment

Before any trade signal is acted upon, the Greeks Engine assesses whether the target strike is viable from a risk-reward perspective:

Field

Details

Delta Filter

MIN 0.20, MAX 0.55. Below 0.20 = too far OTM (lottery ticket). Above 0.55 = deep ITM (high premium, low leverage).

Theta Filter

Daily theta as % of premium must be below 3.0% for weekly expiry and below 1.5% for monthly expiry. Prevents entering options that decay too rapidly.

IV Rank Filter

IV Rank must be below 50 to buy options. Above 50 means IV is expensive relative to historical — unfavourable for buyers.

Bid-Ask Spread Filter

Spread as % of LTP must be below 3%. Wide spreads indicate illiquidity and cause adverse fills.

Premium Range

NIFTY options: ₹30 to ₹300 per unit. BANKNIFTY options: ₹50 to ₹600 per unit. Avoids junk sub-₹10 options and expensive deep-ITM options.

Volume Filter

Minimum 500 contracts traded in the current session before taking entry. Zero-volume options are rejected.

Open Interest Filter

Minimum 10,000 OI. Low OI indicates illiquid strike.



6.5 Greeks Computation Performance

All Greek computations use NumPy vectorised operations, processing the entire option chain (40+ strikes) in under 5 milliseconds.

IV computation is the most expensive step (~15ms per chain). Results are cached per tick to avoid redundant computation.

The engine processes Greeks for both NIFTY and BANKNIFTY concurrently using Python asyncio tasks.

7.3 Strategy 1: Momentum Breakout

Concept

Detects when the underlying index breaks above (bullish) or below (bearish) a significant intraday level with strong momentum, then buys the corresponding ATM option.

Entry Conditions

Breakout Detection: 5-minute candle close above the morning session high (9:15-10:00 AM range) with a body > 0.3% of the open price.

Volume Confirmation: Breakout candle volume must be > 1.5x the 20-candle average volume.

VWAP Alignment: For a CE signal, price must be above VWAP. For PE, price must be below VWAP.

Trend Filter: 5-minute SuperTrend must be aligned with the signal direction.

RSI: Between 45 and 70 for CE entry; between 30 and 55 for PE entry.

Strike Selection

Buys ATM or 1 strike OTM (if delta >= 0.30) to balance cost and leverage.

Prefers options with 2-7 days to expiry for optimal leverage.

Exit Conditions

SL: 40% of premium paid.

Target: 80% profit activates trailing SL at 50% profit from peak.

Time exit: Square off by 3:15 PM if not already exited.

Reversal exit: If price closes back inside the breakout range on a 5-minute candle.

7.6 Strategy 4: India VIX Mean Reversion

Concept

India VIX is a measure of expected 30-day volatility for NIFTY. When VIX spikes sharply, IV on options becomes inflated. The bot avoids buying during VIX spikes and instead looks for IV crush opportunities.

VIX Spike Entry Block: If India VIX rises > 5% in a single session, the bot pauses new entries for both instruments.

Post-Spike Play: After a VIX spike (VIX > 20), if VIX starts falling back, this signals IV crush — buy ATM straddles (both CE + PE) to benefit from the directional move that typically follows.

VIX Data Source: India VIX token is available via SmartAPI as NSE:INDIA VIX. Subscribe in Mode 1 (LTP only).

7.8 Strategy 6: Opening Range Breakout (ORB)

The Opening Range is defined as the High-Low range of the first 15 minutes (9:15 to 9:30 AM). A breakout above or below this range provides a reliable momentum signal for the rest of the session.

Opening Range is computed from the first three 5-minute candles.

Breakout is confirmed when a subsequent 5-minute candle closes outside the range by at least 0.2%.

ATM or 1-OTM option in the breakout direction is purchased immediately after confirmation.

Target: 2× the opening range width (in index points, converted to expected option premium move).



7.9 Signal Aggregator & Conflict Resolution

When multiple strategies simultaneously generate signals for the same instrument, the Signal Aggregator resolves conflicts:

Field

Details

Same Direction Agreement

If 2 or more strategies agree on CE or PE, signal confidence is boosted by 15% each. Entry is prioritised.

Conflicting Signals

If one strategy says CE and another says PE for the same instrument simultaneously, both signals are held for 5 minutes. If conflict persists, neither is executed.

Priority Order

OI Buildup > ORB > Momentum Breakout > PCR Reversal > Event Driven > VIX Mean Reversion.

Cooldown Period

After a losing trade on an instrument, that instrument's strategies are paused for 30 minutes.

Instrument Isolation

NIFTY and BANKNIFTY signals are processed completely independently. A bad NIFTY trade does not block BANKNIFTY signals.




8. Module 6 — Risk Manager

The Risk Manager is the most critical component of the entire system. It acts as the final gatekeeper before any order is placed, enforcing multiple layers of protection to prevent catastrophic losses. All risk parameters are configurable in settings.yaml.

8.3 Position Sizing Algorithm

def compute_position_size(signal, account_value, daily_loss_used):

    # Maximum spend is the minimum of:

    # 1. Per trade risk limit (₹2,000)

    # 2. Remaining daily instrument budget

    # 3. 2% of account value

    max_spend = min(

        PER_TRADE_RISK,

        instrument_budget - daily_loss_used,

        account_value * 0.02

    )



    lot_size   = registry.get_lot_size(signal.instrument)

    premium    = signal.entry_ltp

    cost_1_lot = premium * lot_size



    lots = int(max_spend / cost_1_lot)

    lots = max(1, min(lots, MAX_LOTS_PER_TRADE))  # 1 to 3 lots

    return lots

The margin check is performed at the last possible moment (just before order placement) to get the most accurate available margin figure.

9.2 Smart Limit Price Computation

Placing a LIMIT order too aggressively (at bid) risks non-execution. Placing too passively (above ask) causes overpayment. The execution engine uses a dynamic pricing model:

def compute_limit_buy_price(bid, ask, ltp):

    spread = ask - bid

    spread_pct = spread / ltp * 100



    if spread_pct < 1.0:

        # Tight spread: pay ask price for immediate fill

        return round_to_tick(ask)

    elif spread_pct < 2.0:

        # Medium spread: pay ask + 0.5% buffer

        return round_to_tick(ask * 1.005)

    else:

        # Wide spread: pay mid + 20% of spread

        mid = (bid + ask) / 2

        return round_to_tick(mid + spread * 0.2)



9.3 Order Placement Sequence

Step 1 – Pre-Flight: Fetch fresh LTP using ltpData() REST call. Verify that the price has not moved more than 2% from signal price (stale signal check).

Step 2 – Liquidity Check: Verify bid-ask spread is still within tolerance. Abort if spread has widened beyond threshold.

Step 3 – Margin Final Check: Fetch getRMS() and verify available margin.

Step 4 – Build Order: Construct order parameters with dynamically computed limit price.

Step 5 – Submit Order: Call placeOrder() via SmartAPI. Capture order_id from response.

Step 6 – Track Order: Register order_id in OrderTracker with status PENDING.

Step 7 – Fill Confirmation: Poll orderBook() every 2 seconds for up to 30 seconds to confirm fill.

Step 8 – Modify if Unfilled: If order not filled within 15 seconds, check LTP and modify order price upwards by 0.5% (max 2 modifications).

Step 9 – Cancel if Still Unfilled: If not filled after 30 seconds, cancel order and log as missed opportunity.

10.3 Trailing Stop Loss Logic

def update_trailing_sl(position, current_ltp):

    pnl_pct = (current_ltp - position.entry_price) / position.entry_price



    # Activate trailing SL when profit reaches 100%

    if pnl_pct >= 1.00 and not position.trailing_sl_active:

        position.trailing_sl_active = True

        position.trailing_sl_price = position.entry_price * 1.70  # Lock 70%

        alert('Trailing SL activated at +70% profit')



    if position.trailing_sl_active:

        # Update peak price

        position.peak_price = max(position.peak_price, current_ltp)



        # Trail SL at 30% below peak

        new_sl = position.peak_price * 0.70

        if new_sl > position.trailing_sl_price:

            position.trailing_sl_price = new_sl



        # Trigger exit

        if current_ltp <= position.trailing_sl_price:

            return ExitSignal('TRAILING_SL', current_ltp)



10.4 Position Monitoring Loop

The position monitor runs as an async task polling every 500 milliseconds:

For each open position, retrieve the latest tick from the FeedManager cache.

Run all exit checks in priority order (Hard SL first, then soft SL, target, trailing SL, time exits, theta, signal reversal).

If any exit condition is triggered, immediately call ExecutionEngine.place_exit_order().

Update position's current_ltp, unrealised_pnl, unrealised_pnl_pct, and peak_price on every cycle.

Persist the updated position snapshot to the database every 10 seconds.

14.3 Backtesting Assumptions & Limitations

Slippage Model: Buy orders filled at ask + 0.5% slippage. Sell orders at bid - 0.3% slippage.

Brokerage Costs: ₹20 per executed order (AngelOne flat fee) + STT + exchange charges (approximately 0.05% of premium).

IV Assumption: When tick-level IV is unavailable, IV is interpolated from daily OHLCV of NIFTY VIX.

Survivorship Bias: Option chain data must include delisted/expired contracts to avoid survivorship bias.

Look-Ahead Bias Prevention: All indicators are computed strictly on past data. No future values leak into decisions.

15.2 Circuit Breakers

API Call Rate Limiter: AngelOne SmartAPI allows 10 requests/second on REST. The bot implements a token-bucket rate limiter to stay within limits.

Order Flood Prevention: Maximum 3 orders per minute. If more than 3 order attempts happen in 60 seconds, the execution engine is paused for 2 minutes.

Runaway Trade Prevention: If more than 8 trades are executed in a single day, a human confirmation via Telegram is required for further trades.

Negative Premium Detection: If a computed limit price is zero or negative (data anomaly), the order is aborted immediately.



15.3 Startup Sequence & Health Checks

Every morning at 08:30 AM, the bot runs a pre-market startup sequence:

Download and parse latest instrument master from AngelOne.

Verify API credentials and generate session tokens.

Load and validate risk configuration from YAML file.

Fetch previous day's trade log from broker and reconcile with local database.

Compute overnight IV Rank updates for NIFTY and BANKNIFTY.

Build option chain token lists for the day's expiries.

Test WebSocket connection and verify tick receipt for at least one token.

Send startup health report via Telegram.

Begin live trading at 09:20 AM (5 minutes after market open to avoid opening volatility).

17.2 Dual-Instrument Concurrent Processing

A key architectural feature is the simultaneous, independent processing of NIFTY and BANKNIFTY. The following design decisions support this:

Separate Queues: FeedManager maintains two independent asyncio Queues — nifty_queue and banknifty_queue. Ticks are routed to the appropriate queue based on the instrument token.

Parallel Processing Tasks: Two asyncio tasks run concurrently — process_nifty_ticks() and process_banknifty_ticks() — consuming from their respective queues.

Independent Risk Budgets: NIFTY and BANKNIFTY each have their own daily loss budget. A bad run on one does not immediately block the other.

Shared Capital Pool: While budgets are tracked independently, the total capital and position count limits are shared across both instruments.

Isolated Signal Aggregators: Each instrument has its own SignalAggregator instance, so a signal conflict on NIFTY has no effect on BANKNIFTY signal processing.

Concurrent Order Placement: asyncio.gather() allows simultaneous order placement for NIFTY and BANKNIFTY without one blocking the other.




18. Main Event Loop — Complete Pseudocode



async def main():

    # ── Startup ──────────────────────────────────────────────────

    session  = SessionManager()

    await session.login()

    registry = InstrumentRegistry()

    await registry.load_master()

    feed     = FeedManager(session)

    chain_mgr = OptionChainManager(registry)

    greeks   = GreeksEngine()

    risk     = RiskManager(config.risk)

    executor = ExecutionEngine(session.api)

    pos_mgr  = PositionManager(executor)

    portfolio = PortfolioManager()

    alerter  = TelegramAlerter()



    strategies = [MomentumBreakout(), OIBuildup(),

                  PCRReversal(), OpeningRangeBreakout(),

                  EventDriven()]



    nifty_agg  = SignalAggregator('NIFTY', strategies)

    bnf_agg    = SignalAggregator('BANKNIFTY', strategies)



    await feed.connect()

    await feed.subscribe_all_tokens(registry)

    await alerter.send_startup_report()



    # ── Main Loop ────────────────────────────────────────────────

    async def process_instrument(instrument, aggregator):

        queue = feed.get_queue(instrument)

        async for tick in queue:

            # Update option chain with new tick

            chain_mgr.update(instrument, tick)

            snapshot = chain_mgr.get_snapshot(instrument)



            # Recompute Greeks for ATM +/- 3 strikes

            greeks.refresh(snapshot)



            # Check exit conditions for open positions

            for pos in portfolio.get_open(instrument):

                exit_sig = pos_mgr.check_exit(pos, tick)

                if exit_sig:

                    order = await executor.exit(pos, exit_sig)

                    portfolio.close_position(pos, order)

                    await alerter.on_exit(pos, exit_sig)



            # Generate new signals

            signal = aggregator.evaluate(snapshot)

            if signal:

                approval = risk.approve(signal, portfolio)

                if approval.ok:

                    lots  = risk.size(signal, portfolio)

                    order = await executor.buy(signal, lots)

                    if order.status == 'COMPLETE':

                        portfolio.open_position(order, signal)

                        await alerter.on_entry(order, signal)



    # ── Run NIFTY and BANKNIFTY concurrently ─────────────────────

    await asyncio.gather(

        process_instrument('NIFTY',     nifty_agg),

        process_instrument('BANKNIFTY', bnf_agg),

        pos_mgr.monitoring_loop(),       # 500ms position check loop

        feed.heartbeat_loop(),            # WebSocket keepalive

        scheduler.run_eod_tasks()         # 3:20 PM square-off

    )



asyncio.run(main())



NOTE: The NIFTY and BANKNIFTY processing pipelines run as concurrent asyncio tasks within a single Python process. This avoids the overhead of multiprocessing while achieving effective concurrency through the async I/O model — appropriate since the bot is I/O-bound (waiting on network ticks), not CPU-bound.
